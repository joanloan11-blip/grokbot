# Test-Driven Development

## Обзор
Пиши падающий тест до кода, который его делает зелёным. Для баг-фиксов сначала воспроизведи баг тестом. Тест — доказательство, "выглядит верно" не считается.

## Когда использовать
- Любая новая логика/поведение
- Исправление любого бага (Prove-It Pattern)
- Изменение существующей функциональности
- Обработка краевых случаев

**Не использовать:** чисто конфигурационные изменения, правки документации, статика без влияния на поведение.

## Сначала выясни стек
Цикл TDD универсален, команды — нет. Перед первым тестом:
- Язык и система сборки — `package.json`, `pyproject.toml`, `go.mod`, `Cargo.toml`, `Makefile`, `pom.xml`
- Обёртки в репо — предпочитай `./gradlew`, `make test`, локальные скрипты глобальным
- Тестовый фреймворк и конфиг — как запустить один тест vs весь набор
- Существующие конвенции — где лежат тесты, как названы
- Документированные команды — README, CONTRIBUTING, CI

Никогда не предполагай `npm test` по умолчанию — у Gradle/Cargo/pytest свой эквивалент.

## Цикл TDD
```
    RED              GREEN             REFACTOR
 Падающий тест → минимум кода → чистим реализацию → (повтор)
```

### Step 1: RED — пишем падающий тест
Тест пишется первым и ДОЛЖЕН упасть. Тест, который сразу проходит, ничего не доказывает.

### Step 2: GREEN — делаем зелёным
Минимальный код, чтобы пройти. Не переинженеривай.

### Step 3: REFACTOR — чистим
С зелёными тестами улучшай без смены поведения: вынеси общее, улучши имена, убери дубли, оптимизируй при необходимости. Гоняй тесты после каждого шага.

## Prove-It Pattern (баг-фиксы)
Когда приходит багрепорт, НЕ начинай с фикса. Начни с теста, воспроизводящего баг:
```
Баг пришёл
  → пишем тест, демонстрирующий баг
  → тест ПАДАЕТ (баг подтверждён)
  → реализуем фикс
  → тест ПРОХОДИТ (фикс доказан)
  → прогон полного набора (регрессии?)
```

## Завершение
Гоняй focused-тест в цикле и полный набор перед завершением. Задача не готова, пока тесты не зелёные.
